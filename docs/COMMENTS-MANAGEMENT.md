# 评论结构与后台管理

已应用追加迁移 `011_comments.sql`。当前只实现数据库、管理员 Core 服务、HTTP 接口、OpenAPI 和后台页面；前台评论发布和展示暂不实现。未新增依赖，未修改 Custom。

## 两级与相互回复

- 一级评论 `root_id`、`reply_to_id` 都为空。
- 二级回复 `root_id` 始终指向所属一级评论；`reply_to_id` 指向实际回复对象，可以是一级评论或同串二级回复。
- A 为一级评论，B 回复 A、C 回复 B、D 回复 C 时，B/C/D 都归属 A，展示层级仍为两级。
- 数据库触发器和外键阻止跨内容、跨串、把二级评论当作一级归属，以及修改既有回复关系。正文最多 5000 字符。

## 状态与删除

单条状态为 `visible`、`hidden`、`deleted`。一级评论另有 `thread_hidden` 开关。

单条隐藏可恢复，只影响这一条。整串隐藏只更新一级评论上的开关，不逐条改写回复；恢复整串时，原来单独隐藏或删除的评论保持原状。二级回复返回的 `threadHidden` 是当前有效整串开关。

后台“删除正文”清空正文、设置删除时间，保留编号、作者关联和回复关系。正文不可通过恢复显示找回；审计不保存正文快照。删除一级评论或某条回复不会连带删除其他回复。禁止继续直接回复已删除评论，但可回复该串仍存在的其他评论。旧备份可能含有删除前的数据，其保留周期仍需后续确定。

数据库保留关系不等于前台必须展示“已删除”占位。后续前台可隐藏已删除叶子，保留仍有效的回复和必要的回复对象信息。后台需要显示已删除状态以便管理。永久删除所属内容时，其评论随内容删除，管理操作记录保留。

## 管理入口与接口

- `/admin/comments`：按内容编号、单条状态筛选，游标分页，每页最多 30 条，只读取 120 字符预览。
- `/admin/comments/[id]`：当前评论、所属一级评论、直接回复目标与同串二级回复分页；按编号倒序，不递归加载整串。
- `/admin/audit?type=comments`：管理记录，包含操作人、对象编号、动作和时间，不含正文。
- GET `/api/v1/admin/comments`、GET/PATCH `/api/v1/admin/comments/{id}`、GET `/api/v1/admin/audit/comments`：均要求管理员身份；写入校验来源、请求体大小、动作白名单和版本，并在事务中写审计。Core 服务同样校验权限。

所有写操作先锁定一级评论，再锁定目标评论，避免整串与单条操作互相覆盖。版本冲突返回 409。整串控制与单条状态独立。
