# 精选置顶、用户资料和站内通知

2026-10-15：追加迁移 015、016、017 已应用；未新增依赖，未覆盖 Custom。继续采用 Core 共用服务、薄 HTTP 适配层和公开扩展契约，暂不做用户私信。

## 内容运营

内容表新增 featured、featured_at、pin_level（0–3）。精选与置顶独立；设置精选时记录时间，取消时清空时间，重复保存保留原精选时间。置顶级别越高，置顶优先排序时越靠前。创建默认非精选、不置顶；更新请求省略 featured/pinLevel 时保留原值，兼容旧调用方。沿用管理员授权、内容版本冲突及内容操作记录。

后台编辑入口已加入精选与置顶，列表显示徽标并提供筛选。公开和后台列表支持 featured/pinned=all|yes|no，以及 sort：

| 值 | 顺序 |
| --- | --- |
| latest | 内容编号倒序，兼容原有默认顺序；后台标为“最新创建” |
| published | 首次发布时间倒序，同时间按编号倒序 |
| updated | 最近更新时间倒序，同时间按编号倒序 |
| priority | 置顶级别、首次发布时间、编号依次倒序 |

首页内容读取使用 priority，仍只返回已发布内容。精选不会自动置顶。没有引入热门评分或人工排序权重。

latest 保持数字游标兼容；其余顺序使用包含排序方式、精确到微秒的时间、编号和置顶级别的复合游标，前台直接透传 nextCursor，不自行解析。切换排序须清除旧游标；不匹配返回 400。分页中内容或运营标记变化按当前状态生效，不提供跨请求快照。

数据库先按筛选和排序确定至多 31 个编号，再为本页读取摘要、分类和标签，避免对排序前的大量记录计算 JSON。索引覆盖按状态的发布、更新、置顶顺序，以及精选筛选。

## 用户资料和扩展

账号身份、邮箱、权限仍留在原用户表；user_profiles 单独保存 bio（500 字符）、homepage（500 字符、无账号密码的 HTTPS 地址）、版本和更新时间。无资料行时返回空资料、版本 0，首次并发保存也通过版本校验只允许一方成功。

用户通过 GET/PATCH `/api/v1/account/profile` 管理自己；管理员通过 GET/PATCH `/api/v1/admin/users/{id}/profile` 编辑指定用户；GET `/api/v1/users/{id}/profile` 只读公开资料，禁用或不存在用户返回 404。资料接口不修改账号权限。后台“我的账号”和“用户详情”均有资料编辑卡片，客户端只接收编辑所需的介绍、主页及版本，不传入私密扩展数据。

user_extensions 为一对一、带 schema_version 的 JSONB。Custom 可在 registerCustom 返回 profileExtension，使用已有字段定义能力注册最多 20 个文本、数字、布尔或枚举字段。每个字段可设范围、必填及 public；未明确 public=true 的扩展不会出现在公开接口，Schema 版本不匹配时也不会公开旧字段。未注册的字段不能写入，扩展请求最多 8KiB；数据库有对象类型和体积边界。

Core 的 createProfileService(definition) 可直接复用；宿主通过 apps/web/lib/profiles.ts 组合 Custom 注册。更新中省略 data 会保留原扩展，所以修改介绍不会擦掉 Custom 数据；显式提交 data 时校验字段和存储 Schema 版本。常用于检索/关联的大型专属数据应以后迁入正式字段或独立业务表，不无限堆入 JSON。

资料变更在 user_profile_audit 记录操作人、目标、变更字段名称与时间，不保存介绍或私密 JSON 的前后快照。该记录当前保存在数据库，未新增全局审计列表标签页。

## 站内通知

通知类型：reply、content_reacted、comment_reacted、follow、system。回复通知发给直接回复对象的作者；一级评论通知内容作者；表情通知对应内容/评论作者；关注通知被关注者。不对同一次回复同时通知全部上级，不通知自动操作的本人。收藏不通知。

活动记录和关注表的触发器在同一事务中产生通知；重试不重复。表情取消/重加和重复关注复用既有通知，不重置已读时间、不反复顶到最新位置。历史活动不会在本次升级时批量补发通知；升级前已经存在的表情活动也不因切换表情而补发旧提醒。

通知只保存来源关联，不保存用户内容的正文快照。列表、未读数、详情和已读操作共用可见性规则：账号禁用、内容下架、评论隐藏/删除、整串隐藏，以及表情/关注取消后，相应通知暂不显示、不计入未读；恢复可见后保留原有已读状态。实际删除来源或关联账号按外键清理通知。通知详情每次重新检查归属和可见性，无法读取其他用户通知，也不隐式改变已读状态。

| 接口 | 行为 |
| --- | --- |
| GET `/api/v1/account/notifications` | 当前账号，status=all|unread，可见性筛选后每页 30 条 |
| GET `/api/v1/account/notifications/{id}` | 当前账号的一条当前可见通知 |
| GET `/api/v1/account/notifications/unread-count` | 当前可见未读数量 |
| PATCH `/api/v1/account/notifications/read` | ids 最多 100 个，或 through 指定本次读取的最新编号，避免把后来到达的消息一起标读 |
| POST `/api/v1/admin/notifications` | 管理员向单个有效用户发送纯文本系统通知 |

系统通知输入 recipientId、key、title、body。key 用于发送幂等，相同发送人、接收人和 key 对应一条消息；相同 key 改正文返回 409。不能传入任意跳转 URL、操作者身份或消息类型。系统通知允许管理员向自己发送；未提供全站广播、用户私信、邮件、推送或实时长连接。

后台新增 `/admin/notifications`，查看当前管理员自己的通知、未读数和分页，支持标读及发送系统通知。从用户详情进入可自动带入接收人。普通用户后续通过相同 Core/API 接入前台，不需要另一套通知系统。

## 验证与性能

生产构建、类型检查、68 项安全测试、6 项维护测试通过。覆盖四种内容排序和微秒游标、运营标记兼容/权限/版本、资料地址校验和并发保存、扩展公开白名单与版本、通知自操作去重/归属/已读边界/隐藏过滤/分页及系统消息幂等。修复了旧编号 Schema 对非数字输入直接 BigInt 转换导致的异常。

真实 pg_dump/pg_restore 已验证资料、扩展、通知、来源活动及关注关系；旧 16 表备份仍可恢复到独立新目标。备份清单新增四张资料/通知表。

`pnpm test:community` 使用隔离数据库：2 万内容、6 万通知，其中目标账号有 5000 条可见及 5000 条隐藏通知。本地预热缓存、单进程结果：全部状态置顶排序 P95 从 24.65ms 降至 3.04ms，已发布置顶 1.22ms，更新排序 0.95ms，精选筛选 0.91ms；资料读取 0.35ms；最新 5000 条通知被隐藏时列表 17.19ms，可见未读精确计数 13.65ms。未读数计算开销随当前账号待筛选消息增长，本版不增加轮询或计数缓存。结果不代表生产并发容量。

报告 `.local/performance/community-admin-before.json`、`community-admin.json`。资源报告 `.local/performance/community-after.json`：公开首页 JS 8 个/570454 字节、CSS 1 个/4848 字节保持原值，公共客户端清单无后台模块；账号后台新增约 2KB JS、共用后台 CSS 增加约 1KB，请求数没有增加。

桌面和 390px 手机视口实际验证精选/置顶保存、用户资料保存、通知标读和向临时测试用户发送系统通知。手机无页面横向溢出，消息操作按钮 44px；已恢复并验证批量修改中误写的后台样式。临时验证用户、内容、消息和相关操作记录在验收后清理。
