# 用户关注

已应用追加迁移 `013_user_follows.sql`。提供关注、取消关注、当前账号的关注列表和粉丝列表、批量关系查询，以及网站/APP 共用的 Core 服务和接口。未新增依赖，未修改 Custom 或前台页面。

## 数据和行为

`user_follows` 每行表示 follower_id 关注 following_id，两个编号组成主键，防止重复；数据库检查禁止关注自己。双方都是用户外键，实际删除用户时清理两个方向的关系。独立递增关系编号用于稳定分页，两个方向分别建立用户/编号倒序索引。

互相关注是 A→B 与 B→A 两条记录同时存在，不保存冗余互关状态。取消一个方向不改变另一个方向。重复关注不改变原关系编号与时间；取消后重新关注获得新编号。

关注者必须登录且未被禁用，新增关注的目标也必须存在且未被禁用。已禁用目标暂不出现在列表和批量摘要中，但保留原关系，解除禁用后恢复显示；取消自己的既有关系仍然允许。不存在对象的取消操作幂等成功。所有操作只作用于登录用户，禁止通过请求指定他人作为关注发起者。

写入先取得用户权限锁的共享锁，再按用户编号顺序取得行共享锁，与后台禁用/角色变更采用相同的权限入口顺序。不同关注写入可并行；权限变更会等待当前关注事务完成，后续关注重新检查用户状态。事务失败释放锁并回滚。

## 服务与接口

Core 导出 `setFollow`、`getOwnFollows`、`getFollowStates`。公共契约在 `packages/extension-api/follows`，HTTP 层复用 Core 的授权、校验和业务规则。

| 方法及路径 | 用途 |
| --- | --- |
| PUT `/api/v1/users/{id}/follow` | `{active:true}` 关注；false 取消 |
| GET `/api/v1/account/follows/following` | 当前账号的关注列表 |
| GET `/api/v1/account/follows/followers` | 当前账号的粉丝列表 |
| POST `/api/v1/follows/summary` | `{ids:["用户编号",...]}` 批量关系状态 |

全部接口要求登录，响应 no-store；PUT/POST 额外检查来源、JSON 类型及 16KiB 请求体边界。Core 内执行共享读写限流，严格输入字段白名单。错误沿用 `{error:{code,message}}`，OpenAPI 已同步。

列表按关系编号倒序，每页最多 30 项，用 `before=nextCursor` 获取更早关系；只读取 31 行判断下一页，不执行总数查询。返回用户编号、最多 100 字符的名称、关系编号/时间，以及相对当前用户的 `following`、`followsMe`、`mutual`，不返回邮箱、角色、会话或禁用原因。此处仅实现当前账号自己的列表，不开放任意用户的关系名单。

批量查询最多 30 个不同用户编号，一次查询通过正反方向索引返回关系状态；不存在或已禁用用户省略。查询自身时三个状态均为 false。列表也在同一个查询中联查反向关系，不逐个用户调用服务。

## 验证

2026-10-15：生产构建和类型检查通过；安全测试 52 项、维护测试 5 项、模拟数据性能测试通过。新增测试覆盖未登录访问、请求来源/大小/白名单、禁止指定他人身份、并发幂等、互关与独立取消、关注和粉丝两方向分页、禁用隐藏/恢复、在途关注与禁用的锁协调、外键清理及共享限流。

实际 pg_dump/pg_restore 已验证恢复两个方向的关注关系，备份计数包含 user_follows。旧的 16 表备份仍可恢复至独立新目标；验证目标随后清理。

模拟数据包含 510000 条关注关系，当前测试用户关注和粉丝各 5000 条。数据库查询 P95：30 人关系批量 0.73ms，关注列表 0.76ms，粉丝列表 0.87ms，较深关注页 0.61ms；均为单条查询并命中相应索引。关注/取消两个完整事务合计 P95 2.76ms。含登录校验的列表 HTTP P95 约 16.8ms。报告 `.local/performance/admin-scale-follows.json`；本地缓存预热、单进程结果，不代表生产并发容量。

资源报告 `.local/performance/follows-after.json`：公开首页 JS/CSS 请求数和字节数保持原值，公共客户端清单未引入后台模块。
